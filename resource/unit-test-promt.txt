# Rules (best practices)

## Structure & naming
- JUnit 5. One scenario per test method. Arrange-Act-Assert with `// Given / // When /
  // Then` comments.
- Test method name format: `methodUnderTest_givenState_expectedOutcome`
  (e.g. `calculateTotal_emptyList_throwsIllegalArgumentException`).
- Place the test class in the same package as the class under test.

## Isolation
- Plain services/components: `@ExtendWith(MockitoExtension.class)`, dependencies as
  `@Mock`, the system under test as `@InjectMocks`.
- Do NOT use `@SpringBootTest` for a pure unit test.
- Spring MVC controllers: use `@WebMvcTest` + `MockMvc`, mock the service layer.

## Assertions
- Use AssertJ: `assertThat(actual).isEqualTo(expected)`. For exceptions:
  `assertThatThrownBy(...).isInstanceOf(...).hasMessage(...)`.
- Assert concrete, literal expected values. Never compute the expected value using the
  same logic as the production code.
- Assert observable behavior/output, not implementation details.

## Mocking
- Stub only the interactions the test actually exercises. Do not over-mock.
- When the arguments passed to a dependency matter, capture and assert them with
  `ArgumentCaptor` instead of matching with `any()`.
- Verify only interactions relevant to the behavior under test.

## Coverage & cases
- Cover: happy path, every error/exception branch, validation failures, boundary
  values, null/empty inputs.
- Use `@ParameterizedTest` when the same behavior is checked across several inputs.
- Test through the public API; do not test private methods directly.

## Test data & determinism
- Build test data with the real constructors/fields of the actual classes — do not
  guess. Extract repeated setup into small helper methods/builders.
- No dependence on real time, randomness, network, filesystem, or `Thread.sleep`. If
  the code uses `now()` or random values, note they should be injected (e.g. `Clock`)
  and test deterministically.
- No control-flow logic (loops/if) inside test methods.

## Integrity (important)
- Do NOT modify the production code. If a test can only pass by changing production
  behavior, the production code may have a bug: keep the test asserting the CORRECT
  expected behavior, mark it (`// BUG?: ...` or `@Disabled("possible bug: ...")`), and
  call it out explicitly in the Notes section.
- Do not silently work around problems. List all assumptions, unknowns, and gaps
  separately at the end.

# Output format
1. Analysis (bullets)
2. Test-case list (Given/When/Then)
3. Complete test class (single code block)
4. Notes: assumptions, TODOs, suspected bugs
